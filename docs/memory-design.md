# Otherone Memory Module Design Draft

本文记录 Otherone 记忆模块的设计草案。当前阶段只描述设计，不包含 Rust 实现。

## Current Status

当前框架还没有独立的 `memory` 模块。现有的会话历史由 `otherone-storage`
负责保存，结构接近常见的 session + message/entry 模型，因此可以视为短期记忆的基础。

计划新增的 memory 模块分为两层：

- 短期记忆：沿用当前 session 和 message/entry 结构，用于保存当前会话和历史上下文。
- 长期记忆：使用 Self-evolution 树结构保存可复用信息，不使用向量数据库作为主要存储方式。

## Core Idea

长期记忆不是在读取时依赖向量相似度临时分类，而是在写入时就让模型判断信息类型并放入树中。

每次用户和 Otherone 的对话都会被评估一次信息可重复使用度。可重复使用度只需要输出
`true` 或 `false`。如果是 `true`，模型还需要输出一个候选记忆节点，最小结构如下：

```json
{
  "storage": "用户比较喜欢吃炸酱面",
  "types": "用户喜欢吃的面食"
}
```

其中：

- `storage` 是节点保存的事实、偏好、规则、身份信息、项目约定等可复用内容。
- `types` 是这个节点的语义类型。它不是固定枚举，而是由模型根据内容生成。
- `types` 应优先具体、垂直，而不是过度宽泛。例如优先使用“用户喜欢吃的面食”，而不是直接使用“用户喜欢吃的食物”。

## Tree Terms

- Headless point：无向头。树的空头节点，本身不保存业务信息。
- Root point：根节点。Headless point 的直属子节点。
- Memory point：普通记忆节点。每个节点都是一个 JSON 对象，至少包含 `storage` 和 `types`。
- Parent/child：父子关系表达语义包含关系。越深的节点，`types` 应该越具体。

## Long-Term Memory Tree

树的基本原则：

1. Headless point 不保存任何实际信息。
2. Root point 是某一类长期记忆的入口。
3. 子节点应该比父节点更加具体。
4. 同类或从属信息应该挂到已有相关节点下面。
5. 当新信息改变了原有分类边界时，树可以自进化：修改节点 `types`，移动节点，合并节点，或者提升抽象层级。

示例一：第一次写入偏好。

用户说：“我平时比较喜欢吃炸酱面。”

评估结果为可复用，模型输出：

```json
{
  "storage": "用户比较喜欢吃炸酱面",
  "types": "用户喜欢吃的面食"
}
```

如果当前树里没有相关节点，该节点可以作为一个 root point。

示例二：后续写入同一大类的新偏好。

用户后来说：“我比较喜欢吃糖醋排骨。”

新节点可以是：

```json
{
  "storage": "用户比较喜欢吃糖醋排骨",
  "types": "用户喜欢吃的菜"
}
```

插入时发现它和已有“用户喜欢吃的面食”相关，但不是同一个精细类型。此时树可以自进化：

- 将原来的上层类型调整为更宽的“用户喜欢吃的食物”。
- 将“用户喜欢吃糖醋排骨”作为其子节点。
- 保持更深节点的类型更具体，例如“用户喜欢吃的面食”“用户喜欢吃的菜”。

这里有一个需要后续明确的设计点：当一个原本保存具体事实的节点被提升为更宽泛分类时，
它的 `storage` 是否也应该被改写为分类摘要，或者保留原始事实作为该分类的代表节点。
更稳妥的实现可能是“节点提升/拆分”：新增一个更抽象的父节点，把原始具体事实和新事实都挂到它下面。

## Write Flow

长期记忆写入流程建议分为以下步骤：

1. 候选内容生成
   - 从本轮用户消息、助手回复、工具结果或完整 turn 中提取候选信息。
   - 初期可以只评估用户消息，降低复杂度。

2. 可复用度评估
   - 使用小而快的模型判断该信息是否值得进入长期记忆。
   - 输出必须是结构化结果：`should_store: true/false`。
   - 判断规则应写入 prompt，例如偏好、身份、长期目标、项目约定、稳定事实更容易入库；一次性问题、临时状态、闲聊噪声不入库。

3. 候选节点生成
   - 如果 `should_store = true`，模型生成候选节点。
   - 最小字段是 `storage` 和 `types`。
   - `types` 优先具体，避免过早归到非常泛的分类。

4. 系统预筛
   - 系统根据关键词、已有 `types`、已有 `storage` 做第一轮候选节点筛选。
   - 目标不是最终判断，而是减少交给模型的候选范围。

5. 模型语义判断
   - 小模型判断新节点与候选节点的关系：
     - same：同一记忆或可合并。
     - parent：新节点比候选节点更抽象。
     - child：新节点比候选节点更具体。
     - sibling：同一大类下的不同具体类型。
     - unrelated：无关。

6. 树操作
   - 没有相关节点：插入为 root point。
   - 找到更宽泛父节点：插入为其子节点。
   - 找到同类兄弟：必要时创建或更新更抽象父节点。
   - 找到重复节点：合并或更新原节点，而不是简单追加。
   - 发现旧分类不合适：允许 retype、reparent、split、merge。

## Retrieval Flow

读取长期记忆的关键是找到起始节点。

当前落地的第一版是由主 Agent 主动调用读取工具：

1. 主 Agent 判断当前请求可能需要长期记忆时，调用 `otherone_recall_long_term_memory`。
2. 主 Agent 传入 `memory_types`，也就是若干个紧凑的 `types` 关键词。
3. 系统按 `types` 对记忆树做模糊匹配，找到一个或多个起始节点。
4. 一旦确定起始节点，就取该节点及其所有子分支。
5. 返回给主 Agent 的内容只包含每个节点的 `storage` 文本，不暴露内部节点 JSON。

这个设计依赖一个前提：子节点比父节点更具体，因此命中某个节点时，它的子树通常都属于可用的补充信息。

为了避免取出过多内容，读取链路需要加入限制：

- 单次允许查询的 `memory_types` 数量。
- 每个 `memory_types` 最多匹配的起始节点数量。
- 最大节点数。
- 最大深度。
- token budget。
- 多个起始节点之间的去重。
- 如果子树过大，可以先摘要再注入。

当前实现已经支持 `memory_types` 数量限制、每个类型的匹配数量限制、返回记忆总数限制，以及跨分支去重。后续如果发现系统关键词匹配不够聪明，可以在系统筛选之后加入小模型重排，让小模型从候选起始节点中做最后选择。

## Self-Evolution Operations

长期记忆树需要支持自进化，而不是只支持 append。

核心操作包括：

- insert：插入新节点。
- merge：合并重复或高度重叠节点。
- retype：修改节点 `types`，让分类更准确。
- reparent：移动节点到更合适的父节点下面。
- promote：创建更抽象的父节点，吸收多个相关节点。
- split：当一个节点混入多个语义时，将其拆成多个节点。
- deactivate：信息过期、冲突或不再可信时，将节点标记为无效，而不是直接删除。

## Possible Node Fields

最小节点只要求：

```json
{
  "storage": "用户比较喜欢吃炸酱面",
  "types": "用户喜欢吃的面食"
}
```

后续实现可能需要扩展字段：

- `point_id`：节点唯一 ID。
- `parent_id`：父节点 ID，Headless point 的直属子节点 parent 为空或指向 headless。
- `children`：子节点 ID 列表，或由存储层通过 parent_id 查询。
- `confidence`：模型对该记忆的置信度。
- `source_session_id`：来源会话。
- `source_entry_id`：来源消息。
- `created_at` / `updated_at`：时间。
- `status`：active/deactivated。
- `version`：节点被自进化修改的版本。

这些字段不是当前阶段必须实现的内容，只是后续落地时可能需要的存储元数据。

## Integration With Existing Framework

短期记忆可以继续使用当前 `otherone-storage`：

- localfile：`.otherone/storage/otherone-storage.json`
- database：`otherone_session`、`otherone_entries`、`otherone_compacted_entries`

长期记忆建议作为独立模块接入 agent loop：

1. 主 Agent 通过工具主动读取长期记忆，并将返回内容作为本轮回答的补充上下文。
2. 主 Agent 通过工具提交可复用信息，写入任务进入长期记忆处理链路。
3. 辅助模型负责最终写入决策，执行树插入和自进化操作。

初期可以先只做 localfile 版本，等算法稳定后再扩展数据库版本。

## Design Advantages

- 写入时分类，读取时可以更稳定地取出结构化子树。
- 不依赖向量数据库，部署成本低，更适合轻量 Rust framework。
- 记忆结构可解释，用户或开发者可以直接查看树。
- 适合保存稳定偏好、长期项目规则、个人习惯、常用约定。
- 自进化能力可以让树从细节逐步长出抽象分类，而不是一开始就固定 taxonomy。

## Design Risks

- 插入时依赖模型判断，早期错误分类可能影响后续结构。
- 树结构天然是单父层级，但真实信息可能属于多个分类。
- `types` 是自由文本，可能产生同义词漂移，例如“喜欢的食物”和“饮食偏好”。
- 节点提升时，`storage` 和 `types` 的抽象层级可能不一致，需要明确规则。
- 检索起始节点如果找错，可能漏掉重要记忆。
- 子树过大时会带来 token 压力，需要预算和摘要策略。
- 自进化操作会修改历史结构，需要保留来源和版本，方便调试和回滚。

## Implementation Direction

建议按阶段实现：

1. 先定义长期记忆的数据模型和本地存储格式。
2. 实现可复用度评估 prompt 和结构化输出 schema。
3. 实现候选节点生成。
4. 实现系统预筛和模型语义判断。
5. 实现插入、合并、提升、移动等树操作。
6. 实现长期记忆检索和子树序列化。
7. 接入 agent loop：调用前读取，调用后写入。
8. 加入调试 API，让开发者能查看、修改、禁用节点。

当前建议先从最小闭环开始：localfile 存储 + 用户消息评估 + 插入树 + 简单检索。
